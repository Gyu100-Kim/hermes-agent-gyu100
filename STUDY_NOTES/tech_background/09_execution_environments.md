# 배경기술 09. 실행 환경 격리 (local / Docker / SSH / Modal / Daytona / Singularity)

## 이 문서에서 다루는 큰 맥락

에이전트가 명령을 실행하는 **격리된 실행 환경(execution environment)** 들을 다룹니다.
같은 에이전트가 로컬 셸부터 원격 컨테이너까지 동일한 방식으로 명령을 돌릴 수 있게
하는 추상화입니다.

## 1. 개념: 왜 격리가 필요한가

- 에이전트가 임의의 셸 명령을 실행하면 **호스트를 망가뜨리거나** 민감정보에 접근할
  위험이 있습니다. 그래서 명령을 **격리된 샌드박스**에서 돌리려 합니다.
- 동시에, 어디서 돌리든 에이전트 코드는 **동일한 인터페이스**로 명령을 보내야
  합니다. 그래야 백엔드를 갈아끼워도 코어가 바뀌지 않습니다 → 추상 기반 클래스로
  통일.

## 2. 백엔드별 개요와 히스토리

- **local** — 호스트에서 직접 실행. 가장 빠르고 단순, 격리는 가장 약함.
- **Docker** — 컨테이너 격리. 2013년 등장 이후 사실상 표준 격리 수단. 재현성과
  의존성 격리가 강점.
- **SSH** — 원격 머신에서 실행. 강력한 GPU 서버나 별도 호스트를 쓸 때.
- **Modal** — 서버리스 클라우드 컴퓨트. 필요 시 원격 컨테이너를 즉석에서 띄움.
- **Daytona** — 개발 환경 프로비저닝 플랫폼. 표준화된 원격 워크스페이스.
- **Singularity(Apptainer)** — HPC(고성능 컴퓨팅)/연구 클러스터에서 흔한 컨테이너
  런타임. 루트 권한 없이도 돌릴 수 있어 공유 클러스터에 적합.

## 3. 동향과 트레이드오프

- **격리 강도 ↔ 속도/편의**의 트레이드오프가 핵심입니다. local은 빠르지만 위험,
  컨테이너/원격은 안전하지만 셋업·지연 비용이 있습니다.
- **파일 가시성**: 원격 백엔드에서는 에이전트가 만든 파일을 호스트에서 보거나 그
  반대가 안 될 수 있어, **파일 동기화/마운트**가 중요한 문제가 됩니다.
- 코딩 에이전트 붐과 함께, "안전하게 코드를 실행하는 샌드박스"가 인프라 상품
  (원격 개발 환경, 서버리스 실행)으로 활발히 나오고 있습니다.

## 4. 이 저장소에서의 구현 연결

- 모든 백엔드는 `tools/environments/` 아래에 있고, 공통 추상 기반 클래스
  `tools/environments/base.py`를 상속합니다.
  [`tools/environments/base.py` 1-7행](../../tools/environments/base.py#L1-L7)
  - **통일된 실행 모델**(3-6행): 모든 명령이 새 `bash -c` 프로세스를 띄우는
    "spawn-per-call" 모델. init 시 세션 스냅샷(env/함수/alias)을 한 번 캡처해 매
    명령 전에 다시 source하고, CWD는 원격은 stdout 마커, 로컬은 임시 파일로 유지.
- 파일 목록(실제 존재하는 백엔드):
  `local.py`, `docker.py`, `ssh.py`, `modal.py`(+`managed_modal.py`, `modal_utils.py`),
  `daytona.py`, `singularity.py`, 그리고 원격 파일 동기화용 `file_sync.py`.
- 에이전트가 쓰는 도구는 [05_tools.md](../05_tools.md)의 `terminal`/`process`
  등이며, 이들은 어떤 백엔드가 활성이든 동일하게 동작합니다. 백엔드 선택은
  설정으로 결정됩니다.
- **설계 의도(ABC로 통일):** `AGENTS.md`의 "같은 카테고리는 하나의 ABC + 오케스트레이터로"
  원칙이 여기서도 적용됩니다. 새 격리 백엔드는 `base.py`의 인터페이스만 구현하면
  코어를 건드리지 않고 추가됩니다. "파일 가시성이 문제면 마운트를 고치지 새 도구를
  만들지 말라"는 rubric도 이 계층을 겨냥한 것입니다.
