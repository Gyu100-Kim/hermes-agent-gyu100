## 1. 개념: 말만 하는 챗봇에서 행동하는 에이전트로

- **함수 호출(function calling / tool calling)**: LLM이 자연어 답변 대신 "이 함수를
  이런 인자(JSON)로 실행해줘"라는 **구조화된 요청**을 내놓을 수 있게 하는 기능입니다.
  프로그램은 그 함수를 실제로 실행하고, 결과를 모델에게 돌려줍니다.
- 이것이 반복되면 **에이전트(agent)** 가 됩니다: 목표 → (생각) → 도구 호출 → 결과
  관찰 → 다시 생각 → ... → 최종 답. "관찰-사고-행동"을 반복한다는 점에서 흔히
  **ReAct(Reasoning + Acting)** 패턴이라 부릅니다.
- 핵심 이점: LLM은 계산·검색·파일 접근·실시간 정보에 약한데, 도구가 그 약점을
  외부 시스템으로 메웁니다. 모델은 "무엇을 할지" 판단만 하고, "실제 실행"은 도구가
  합니다.

## 2. 히스토리(등장 배경)

- 초기에는 프롬프트만으로 "행동을 흉내"내게 했습니다(2022년 ReAct, Toolformer 등
  연구). 모델이 특정 형식의 텍스트를 뱉으면 그걸 파싱해 도구를 실행하는 방식이라
  파싱이 취약했습니다.
- 이후 주요 LLM 제공자들이 **네이티브 함수 호출**을 API에 넣으면서, 모델이 JSON
  스키마에 맞는 도구 호출을 구조적으로 반환하게 되었습니다. 파싱 취약성이 크게
  줄고, 다중 도구·병렬 호출이 표준이 되었습니다.
- 이 흐름이 오늘날의 "코딩 에이전트/개인 비서 에이전트" 붐의 기술적 토대입니다.

## 3. 동향과 주요 결과

- **병렬 도구 호출**: 한 번에 여러 도구를 동시에 요청해 지연을 줄이는 방향.
- **긴 지평선(long-horizon) 작업**: 수십~수백 번의 도구 호출로 복잡한 작업을 끝까지
  수행. 이때 **반복 상한/예산**과 **컨텍스트 관리**가 실패를 막는 핵심이 됩니다.
- **신뢰성 문제**: 잘못된 인자, 존재하지 않는 도구 호출(hallucinated tool), 무한
  루프 등이 실무의 난제이며, 각 프레임워크가 검증·재시도·살균으로 대응합니다.
- 벤치마크(도구 사용 정확도, 에이전트 과제 완수율)가 활발히 발표되지만, 세부 수치는
  모델·설정에 따라 크게 달라지므로 이 문서에서는 특정 수치를 단정하지 않습니다.

## 4. 이 저장소에서의 구현 연결

Hermes는 위 개념을 정면으로 구현합니다.

- **도구 호출 루프**: [04_agent_loop.md](../04_agent_loop.md)에서 본
  `agent/conversation_loop.py`의 `while` 루프가 곧 tool-calling loop입니다.
  <ref_snippet file="/home/ubuntu/repos/hermes-agent-gyu100/agent/conversation_loop.py" lines="1009-1009" />
- **반복 예산으로 long-horizon 제어**: `max_iterations=90`(`run_agent.py` 434행)과
  `IterationBudget`가 무한 루프/비용 폭주를 막습니다.
- **구조화된 도구 스키마**: [05_tools.md](../05_tools.md)의 `tools/registry.py`가
  각 도구의 JSON 스키마·핸들러를 관리하고, `model_tools.py`가 이를 모델에게
  보낼 형식으로 조립합니다.
- **신뢰성 대응**: `registry.dispatch`가 모든 예외를 `{"error": ...}`로 감싸
  (614-644행) 도구 실패에도 루프가 죽지 않게 하고, 존재하지 않는 도구는
  `{"error": "Unknown tool"}`로 응답합니다. 인자 손상 복구
  (`_repair_tool_call_arguments`)와 메시지 살균도 같은 맥락입니다.
- **병렬/역할 교대 규칙**: `AGENTS.md`는 엄격한 역할 교대(두 개의 같은 역할 연속
  금지)와 프롬프트 캐시 보존을 요구하며, 이는 tool-calling을 안정적으로 굴리기 위한
  실무 제약입니다.
